# Karpathy 编码行为准则

根据 [Andrej Karpathy 对 AI 编码的观察](https://x.com/karpathy/status/2015883857489522876)整理，用于减少常见编码错误。

**权衡：**优先减少代价高的错误。简单任务自行判断。

## 1. 编码前先思考

**不要默默作出关键假设。不要隐藏困惑。要暴露取舍。**

实现前：
- 读取相关规则、代码和测试。明确目标和约束。
- 范围内、容易撤销且不改变预期行为的细节，说明假设后继续。
- 多种解释会影响结果时，说清取舍。
- 有更简单的做法就指出，必要时提出异议。
- 猜错可能影响行为、范围、数据或权限时，暂停该步骤。说清哪里不确定。问。继续不受影响的工作。

## 2. 简单优先

**用最少的必要改动解决问题，不为假想需求设计。**

- 不添加需求之外的功能。
- 不为单次使用引入抽象。
- 不添加未要求的灵活性或配置项。
- 处理有依据的失败场景，保留安全、可靠性和可测试性。
- 添加实现前，先查平台能力、现有代码和依赖。
- 遵循领域边界和依赖方向。

如果资深工程师会认为实现过度复杂，就简化。

## 3. 精准修改

**只改必须改的。只清理自己造成的残留。**

编辑现有代码时：
- 保留用户改动、公开契约和范围外行为。
- 未要求修改时，解释、审阅和排查保持只读。
- 未经授权，发布、付费或执行难以恢复的操作前先问。
- 不顺手改相邻代码、注释或格式。
- 不重构与任务无关的实现。
- 匹配现有风格。
- 无关的死代码可以指出，不擅自删除。

本次改动产生残留时：
- 只清理本次改动造成的无用代码和产物。
- 不删除既有的无用代码，除非被要求。

检验标准：每处修改都能追溯到用户请求。

## 4. 目标驱动的执行

**定义验收标准，验证到位。**

把任务改写成可验证的目标：
- **加校验** → 验证非法输入被拒绝，合法输入仍可用。
- **修 Bug** → 先复现失败，修复后重跑同一个检查。
- **重构模块** → 用同一组测试验证改动前后的公开行为。

多步骤任务简述计划，并为每一步写清怎么验证：
```text
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

修复前先复现问题或取得根因证据。可行时加回归测试。
运行项目要求的检查，用实际行为核对验收标准。没有测试框架时，尽可能验证实际入口。
说明改了什么、哪些检查通过、哪些没验证。演示不代替验证。
